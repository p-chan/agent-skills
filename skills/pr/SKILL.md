# PR

PR本文の構成と書き方を定める。

PR本文は、背景、概要、証拠、危険性、補足の順にセクションを書く。補足は書くことがなければ省略し、それ以外は必ず書く。

背景、概要、危険性には、リスクを踏まえたマージ判断に必要な情報を、読み手の負荷が低くなるよう簡潔に書く。判断の経緯など、文脈を知らない読み手が差分から読み取れない、または読み取るのにコストがかかる詳細は補足に残す。

## 作成

リポジトリで主に使われている言語（日本語か英語か）に合わせて、`templates/` 内の対応するテンプレートを使う。

## リポジトリのテンプレート

このスキルを導入したリポジトリでは、このスキルのテンプレートをPR本文の構成の正とする。`.github/pull_request_template.md` と内容が異なるときは、このスキルのテンプレートに従う。

`.github/pull_request_template.md` は、リポジトリの言語に対応する `templates/` のテンプレートで上書きしてよい。

## 分量

背景と概要は、それぞれ次の範囲に収める。概要の図は分量に含めない。

| 言語 | 項目数 | 目安 | 上限 |
| :-- | :-- | :-- | :-- |
| 日本語 | 箇条書き3つまで | 合計140字 | 合計420字 |
| 英語 | 箇条書き3つまで | 合計56語 | 合計168語 |

目安を超えるときも、マージ判断に必要な要点は上限まで本文に残す。その根拠や経緯のうち、文脈を知らない読み手が差分から読み取れない、または読み取るのにコストがかかるものは補足へ移す。

## 用語

ドメイン用語とプロジェクト固有の用語には、PR本文で最初に使うときだけ脚注を付ける。脚注には短い定義を書き、定義箇所があればリンクする。一般的な技術用語には付けない。

```markdown
注文確定時に在庫を引当[^allocation]する。

[^allocation]: 注文に対して在庫を確保し、他の注文に使えなくすること。[`src/inventory/allocation.ts`](https://github.com/OWNER/REPO/blob/main/src/inventory/allocation.ts)
```

## セクション

### 背景

なぜこの変更が必要かを書く。関連するIssueがあれば記載し、マージで閉じるIssueにはクローズキーワード（`Closes #123` など）を使う。

### 概要

変更内容を箇条書きで書き、要点が伝わる最小の図を添える。

図の種類と例は `references/diagrams.md` を参照する。

図は箇条書きの後にまとめて置く。図が複数あるときは、各図の前に何を示す図かを1行で添える。図には、要点の説明に必要な呼び出し、ファイル、props、state、境界だけを残す。

図は1つ使うことも複数使うこともあるが、すべてを使うことはまずない。読み手を圧倒しないよう判断する。

### 証拠

変更が機能する具体的な証拠を、確認したことごとにBeforeとAfterで示す。証拠が複数あるときは、テンプレートの証拠のまとまりを繰り返す。

各証拠には、同じ結果を再現できる手順（実行したコマンド、操作、環境）を添え、`<details>` で畳む。

テンプレートには、BeforeとAfterの書式がスクリーンショット用とそれ以外用の2つある。証拠に合う書式だけを残し、HTMLコメントは消す。

見た目の変更で、環境が整っていればスクリーンショットが最良である。

次に良いのは、テスト結果やコンソール出力などの実行に基づく証拠である。確認した入力と期待値について、変更前と変更後の実際の結果をBeforeとAfterで示す。テストは、何を入力して何を期待したかを擬似コードで示す。「テストが通った」だけでは証拠にならない。

### 危険性

変更が可逆か不可逆かを書く。ロールバックのコストが低いPRほど危険性は低い。破壊的な操作や、戻すのが難しい判断を含む変更は不可逆である。

影響範囲は、このPRの変更が及びうる影響と範囲である。レイアウトのずれ、利用側の破損、モバイル表示など、あらゆる可能性を検討する。

### 補足

背景と概要に収まらなかった情報を書く。レビューしてほしい観点、今回やらないこと、フォローアップ、判断の経緯などである。

文章を続けて書かず、トピックごとに必ず `<details>` で畳む。

```markdown
<details>
<summary>ロック時間を15分にした理由</summary>

...

</details>
```
