# エージェント向け文書

Skill でも指示ファイルでも、エージェントが読む文書の書き方は変わらない。文書の目的は、出力を固定することではなく、作業の進め方を毎回揃えることである。

文書の種類に固有の判断が必要なときは、次を読む。

- Skill を扱うときは [`references/skills.md`](references/skills.md)
- `AGENTS.md` や `CLAUDE.md` などの指示ファイルを扱うときは [`references/instruction-files.md`](references/instruction-files.md)

## エージェントが知らないことだけを書く

エージェントはすでに多くのことを知っている。文書に書くのは、エージェントが知らないことと、書かなければエージェントが違う行動を取ることだけである。

記述ごとに「これを消したら、エージェントは間違えるか」を確かめる。間違えないなら、その記述はトークンを使うだけで行動を変えていないので、削除する。

エージェントに文書を書かせると、モデルがすでに知っていることの説明で膨らみやすい。既存の文書を見直すときは、まず削れる記述を探す。

## 参照の書き方

**参照**は、別の場所にある情報を指し示し、それをいつ読むかを伝える記述である。Skill の `description` も、指示ファイルで別の文書を案内する1行も参照にあたる。

エージェントが参照先を読むかどうかは、参照先の中身ではなく参照の書き方で決まる。必要な情報なのに読まれたり読まれなかったりするときは、本文に書き写す前に、まず参照の書き方を見直す。

参照には、参照先に何があるかと、いつ読むかを書く。

悪い例:

```md
詳しくは `docs/authentication.md` を参照する。
```

良い例:

```md
認証方式を変更するときは `docs/authentication.md` を参照する。
```

いつ読むかは、文書が扱うケースごとに書く。ここでの**ケース**は、実行のたびに通る道筋が変わる、区別できる場合を指す。常に読み込まれる参照は毎回コストがかかるので、本文よりも厳しく削る。

- キーワード（後述）と主な用途を先頭に置く。一覧が長くなると、後半が切り詰められることがある
- 1つのケースにつき、条件は1つだけ書く。同じケースを言い換えただけの条件はまとめる
- 参照先を読めば分かる説明は、参照には書かない

## 2つの負荷

文書や参照を増やすと、次のどちらかの負荷が増える。

- **コンテキストの負荷**：常に読み込まれる情報が、エージェントのコンテキストを占める負荷。コンテキストは、システムプロンプト、会話の履歴、ほかの文書と分け合う資源である。指示ファイルの1行や Skill の `description` は、使われない回にもトークンと注意を消費する
- **認知の負荷**：どの文書があり、それぞれをいつ使うかを、人間が覚えておく負荷。人間が索引の役を担うことになる。人間が判断に関わるために必要な負荷なので、ひたすら減らせばよいものではない。人間の判断が必要な場面には残し、そうでない場面からは取り除く

参照の先に置いた情報は、参照の1行分しかコンテキストを使わない。どこからも参照されていない情報は、人間が存在を覚えていなければ使われない。

## 情報の配置

文書は、手順（エージェントが順に実行すること）と参照情報（定義、ルール、事実など、必要なときに確かめるもの）でできている。手順だけの文書も、参照情報だけの文書も、両方を含む文書もある。

情報は、エージェントがどれだけすぐに必要とするかに応じて、次のどこかに置く。

1. **本文の手順**：エージェントが順に実行すること
2. **本文の参照情報**：実行中に必要に応じて確かめるもの。レビューのルール一覧のように、同列の項目を並べるだけでもよい
3. **別ファイルの参照情報**：本文から参照し、必要なときだけ読ませるもの

別ファイルに移す情報が少なすぎると本文が膨らみ、多すぎるとエージェントが必要とする情報まで見えなくなる。配置を決めるとは、この兼ね合いを取ることである。

移すかどうかは、ケースで判断する。どのケースでも必要な情報は本文に置き、一部のケースでしか使わない情報は別ファイルに移す。手順のある文書に、別ファイルへ移すべき参照情報が混ざっていると、手順が埋もれ、エージェントが手順どおりに進めるかどうかが不安定になる。

### 関連する情報をまとめる

同じ概念の定義、ルール、例外、注意事項は、同じ見出しの下にまとめる。1箇所を読めば関連する情報も目に入るので、エージェントが読み落としにくくなる。見出しと箇条書きで構造を示すと、詰まった段落よりも正確に読み取られる。

同じ内容を複数の場所に書くことも、1つの内容を複数の場所に散らすことも避ける。

### 長すぎる文書

文書が長いほどコンテキストを多く使い、指示が守られにくくなる。どの行も有効で重複がなくても、長すぎれば注意が分散し、大事なルールが埋もれる。参照情報を別ファイルに移し、ケースや手順の区切りで文書を分けて、それぞれが必要な情報だけを持つようにする。

## 指示の書き方

### 守れたかどうか確かめられるように書く

指示は、守れたかどうかを確かめられるくらい具体的に書く。

| 曖昧な指示             | 具体的な指示                                |
| ---------------------- | ------------------------------------------- |
| コードを適切に整形する | インデントは2スペースにする                 |
| 変更をテストする       | コミット前に `npm test` を実行する          |
| ファイルを整理する     | API ハンドラーは `src/api/handlers/` に置く |

### どこまで任せるかを作業に合わせる

指示の細かさは、作業の失敗しやすさと、やり方のばらつきに合わせる。

- **任せる**：やり方が複数あり、状況によって判断を変えるべき作業。方針だけを書き、やり方はエージェントに任せる
- **任せない**：間違えやすい作業、結果を揃える必要がある作業、決まった順序で進める必要がある作業。実行するコマンドや手順をそのまま書く

やり方を複数並べる必要がなければ、標準のやり方を1つ示し、例外の場合だけ別のやり方を書く。

### してほしいことを書く

「〜しない」と書いても、エージェントの注意は否定よりも「〜」の部分に引き寄せられる。禁止したはずの行動がかえって起こりやすくなり、禁止が半ば指示のように働いてしまう。

禁止の代わりに、してほしいことを書く。

悪い例:

```md
不要なコメントを書かない。
```

良い例:

```md
コメントはコードから分からない理由を説明するときに書く。
```

禁止が必要なのは、してほしいことに言い換えられない厳格な制約だけである。その場合も代わりの行動を添えて、エージェントの注意がすべきことに向くようにする。

```md
`main` ブランチに直接 push しない。変更はブランチを作り、PR で提出する。
```

### 用語と強調を揃える

1つの概念は1つの用語で呼び、文書全体で揃える。同じものを別の言葉で呼ぶと、エージェントが別のものとして扱うことがある。

指示どうしが矛盾していると、エージェントはどちらかを適当に選ぶ。複数の文書にまたがる矛盾も含めて、古い指示や食い違う指示を取り除く。

「重要」「必ず」などの強調は、守られない指示1つに絞って使う。多くの行を強調すると、どれも目立たなくなる。

### いずれ古くなる情報を書かない

「2025年8月までは旧 API を使う」のように、時間が経つと誤りになる情報は書かない。今のやり方だけを書き、古いやり方の説明が必要なら別の見出しに分ける。

### キーワードで行動をまとめる

**キーワード**は、モデルが事前学習ですでに知っている短い概念で、エージェントは作業中にこれを手がかりに考える。「トレーサーバレット」や「TDD の red」などがこれにあたる。同じ語を繰り返し使うと、文書のあちこちの記述がその語の意味を肉付けし、少ないトークンで一連の行動を指し示せるようになる。

独自の語を作ってもよいが、はっきり定義する必要がある。作った語にはモデルの既存の知識が結びついていないので、その分の説明にトークンを使う。まずは既存の語を探す。

キーワードは2つの場面で効く。

- **本文**：語が出てくるたびに、エージェントは同じ行動を取る。参照情報の中では、何を探せばよいかを示す
- **参照**：プロンプト、文書、コードで同じ語を使っていると、エージェントはその語から参照先にたどり着きやすくなる

同じ3つの形容を3箇所で繰り返している、1つの考えを伝えるのに1文を費やしている、といった箇所は、1語にまとめられることがある。

- 「速く、毎回同じ結果になり、手間のかからない」→「タイトな（ループ）」
- 「信頼できる確認手段」→「red になる（テスト）」。バグがあるかどうかを、失敗したかどうかという2択で確かめられるようにする

トークンが減るうえに、エージェントが考えるときの手がかりもはっきりする。どの文書にも、キーワード1つで置き換えられる言い換えが残っているつもりで探す。

## 手順と完了条件

手順は実行する順に並べ、何を受け取り何を作るかが分かるように、命令の形で書く。複雑な手順は、エージェントが書き写して進み具合を記録できるチェックリストにする。

各手順の最後には、完了したと判断する条件を書く。作業全体についても、何をもって完了とするかと、それをどう確かめるかを書く。テスト、検証スクリプト、スクリーンショットなど確かめる手段があれば示し、「確かめる、直す、また確かめる」を繰り返させる。

完了条件の良し悪しは、はっきりしているかと、どこまで求めるかの2点で決まる。

### はっきりしているか

エージェントが、終わったかどうかを見分けられるかどうかである。条件が曖昧だと、エージェントは作業が終わる前に終わったとみなしやすい。この先にまだ手順が控えているのが見えていると、注意は「早く終わらせること」に向かいやすい。

悪い例:

```md
実装を十分に理解する。
```

良い例:

```md
変更する関数の呼び出し元をすべて洗い出す。
```

エージェントが作業を早く切り上げてしまうときは、次の順に対処する。

1. 完了条件をはっきりさせる
2. それ以上はっきりさせられず、実際に先を急ぐ様子が見られるときに限り、手順を分けて後の手順を見えなくする

手順を分けて後の手順を隠せるのは、別のエージェントへの引き継ぎやサブエージェントへの委任のように、コンテキストが本当に分かれる場合だけである。同じ会話の中で別の文書を呼び出しても、後の手順は見えたままになる。

### どこまで求めるか

完了条件がどれだけの作業を求めるかである。「変更したモデルをすべて洗い出す」は、「変更点の一覧を作る」よりも徹底した作業を求める。求める水準によって、手順に書いていない調べ物の量が決まる。

これは手順だけの話ではない。「すべてのルールを当てはめる」と書けば、参照情報だけの文書でも漏れのない作業を求められる。

いちばん強い完了条件は、確かめられて、しかも漏れがないものである。

## 文書を分けるとき

文書を分けると、どちらかの負荷が増える。分けるのは、それに見合う効果があるときだけにする。

- **手順の区切りで分ける**：後に控える手順のせいで、目の前の手順が急がれている場合に分ける。逆に手順をまとめると、それぞれの手順から後の手順が見えるようになり、作業を早く切り上げやすくなる
- **呼び出し方で分ける**：Skill に固有の判断なので、[`references/skills.md`](references/skills.md) を読む

## 整理と削除

### 情報の正本

1つの内容は、1つの場所にだけ書く。そうすれば、エージェントの行動を変えたいときの修正も1箇所で済む。同じ内容を複数の場所に書くと、保守の手間とトークンが増えるうえに、その内容が実際以上に重要に見えてしまう。

プロジェクトの環境そのものも正本である。`package.json` のスクリプト、設定ファイル、ディレクトリ構成、`--help` の出力などを文書に書き写すと、その文書はいずれ古くなる写しになる。写しを持つ価値があるのは、調べるのに手間がかかる場合だけである。文書には、調べても分からないことを書く。

- 暗黙の決まりや、ツールの標準と違う決まり
- 判断の理由
- 設定を見ても分からない落とし穴

### 今も必要か

各行が、今も文書の目的に関わっているかを確かめる。もともと作業に関係のない説明や、別ファイルに移すべきケースの記述は不要である。記述している行動や環境が変われば、その行は古くなる。

手入れをしないと、書き足すのは安全で消すのは怖く感じるので、古い記述がたまっていく。そうなると、有効な記述を見つけるのにも古い記述をかき分けなければならない。文書を直すときは書き足すだけで終わらせず、削除、置き換え、統合、分割も検討する。

### 行動を変えない指示

モデルが普段からすることを繰り返す指示は、トークンを使うだけで何も伝えない。1文ずつ、消したらエージェントの行動が変わるかを確かめる。

変わるかどうかは、人間の読み手ではなく、モデルの普段の振る舞いを基準に判断する。意見が分かれたら、議論せずに文書を実際に使って確かめる。行動を変えない文は、言葉を削って短くするのではなく、文ごと消す。

キーワードにも同じ基準を当てはめる。「丁寧に」のように、普段の振る舞いを超えさせる力のない弱い語は、行動を変えない。そのときはやり方を変えるのではなく、もっと強い語に置き換える。

### 確認項目

編集やレビューでは、記述ごとに次を確かめる。

- 消したらエージェントは間違えるか
- ほかの場所と重複や矛盾がないか
- 環境を見ればすぐ分かることではないか
- 守れたかどうか確かめられるほど具体的か
- 一部のケースでしか使わない情報を、別ファイルに移せないか
- 繰り返している言い換えを、キーワードにまとめられないか

## 書き足すときと確かめ方

文書には、起こりそうな問題ではなく、実際に起きた問題への対処を書く。

- 同じ間違いが2回起きたとき
- レビューで同じ指摘を繰り返したとき
- 前回のセッションと同じ訂正や説明を入力したとき

新しく文書を作るときは、まず文書なしで代表的な作業をエージェントにさせ、間違いや足りない情報を記録する。それを補う最小限の内容を書き、同じ作業で違いを確かめる。

文書を変えたら、エージェントの行動が実際に変わったかを見て確かめる。想定と違う順番で読む、参照先を読まない、同じ参照先ばかり読む、といった様子があれば、構成や参照の書き方を見直す。

重複、矛盾、古い記述、行動を変えない指示が見つからず、実際に使って期待どおりに動けば完了とする。
