# エージェント向け文書

エージェントが読む文書は、形式が違っても書き方の原則は共通する。原則に沿って書くと、エージェントは毎回同じ結果ではなく、同じ手順をたどるようになる。

既存の文書を見直すときは、まず削除できる記述を探す。エージェントに文書を書かせると、モデルがすでに知っていることの説明に多くの言葉を費やしやすい。

文書の種類に固有の判断が必要なときは、次を読む。

- Skill を扱うときは [`references/skills.md`](references/skills.md)
- `AGENTS.md` や `CLAUDE.md` などの指示ファイルを扱うときは [`references/instruction-files.md`](references/instruction-files.md)

## 参照と参照条件

参照（context pointer）は、コンテキストの外にある情報を指し、それを読む条件を示す記述である。Skill の `description` も、指示ファイルで文書を案内する1行も、参照にあたる。

エージェントが参照先を読むかどうかは、参照先ではなく参照の文言で決まる。参照先は同じでも、文言が弱いと読まれたり読まれなかったりする。そのときは本文に展開する前に、まず参照の文言を鋭くする。

参照には、参照先が何かに加えて、いつ読むかを書く。

悪い例:

```md
詳しくは `docs/authentication.md` を参照する。
```

良い例:

```md
認証方式を変更するときは `docs/authentication.md` を参照する。
```

参照を読む条件は、文書が扱う分岐（実行ごとに異なる経路をたどる、区別できるケース）ごとに書く。常時読み込まれる参照は毎回コストがかかるので、本文より厳しく削る。

- 中心となる語（後述）を先頭に置く
- 1つの分岐につき、条件を1つ書く。同じ分岐を言い換えた条件は1つにまとめる
- 参照先の本文が伝えている説明は、参照には書かない

## 2つの負荷

文書や参照を追加すると、次のどちらかの負荷が増える。

- **コンテキストの負荷**: 常時読み込まれる情報が、エージェントのコンテキストを占める負荷。指示ファイルの1行や Skill の `description` は、使われない回にもトークンと注意を消費する
- **認知の負荷**: どの文書があり、いつ使うかを人間が把握する負荷。人間が索引の役割を担う。人間が判断に関わるための代償なので、単純に減らす対象ではない。人間の判断が必要な場面にだけ残す

参照を通してだけ読まれる情報のコンテキストの負荷は、参照の1行分で済む。参照がない情報は、人間の認知の負荷だけで支えられる。

## 情報の階層

文書は、手順（エージェントが順に実行するもの）と参照情報（定義、ルール、事実など、必要に応じて確認するもの）でできている。手順だけの文書も、参照情報だけの文書も、両方を含む文書もある。

それぞれの情報は、エージェントがどれだけ早く必要とするかに応じて、次の階層に置く。

1. **本文の手順**: エージェントが順に実行するもの
2. **本文の参照情報**: 実行中に必要に応じて確認するもの。レビューのルール一覧のように、同列の項目が並ぶだけでもよい
3. **外部の参照情報**: 別ファイルに分け、参照を通して必要なときだけ読むもの。同じフォルダーのファイルでも、どこにあるファイルでもよい

下の階層へ移す情報が少なすぎると本文が膨らみ、多すぎるとエージェントが必要とする情報まで隠れる。この2つの釣り合いを取ることが、配置の判断である。

情報を下の階層へ移すと、本文を読みやすく保てる。移すかどうかは分岐で判断する。すべての分岐で必要な情報は本文に置き、一部の分岐だけで必要な情報は参照の先へ移す。手順がある文書に外部へ移すべき参照情報が残っていると、手順が埋もれ、エージェントが手順に従うかどうかが不安定になる。

### 関連情報をまとめる

同じ概念の定義、ルール、例外、注意事項は、同じ見出しの下にまとめる。ひとつを読めば関連する情報も一緒に目に入り、エージェント向けに書かれたドキュメントとして読める。

同じ意味を複数箇所に書く重複と、ひとつの意味を複数箇所に分散させることは、どちらも避ける。

### 長すぎる文書

すべての行が有効で重複がなくても、文書が長すぎると注意が薄まり、関連性を保つべき行も増える。参照情報を参照の先へ移し、分岐や手順列で分割して、各経路が必要な情報だけを持つようにする。

## 手順と完了条件

手順は実行順に並べ、各手順の最後に、完了したと判断する条件を書く。完了条件には、明確さと要求水準の2つの性質がある。

### 明確さ

エージェントが、完了したかどうかを判別できるかという性質である。曖昧な条件は、手順が本当に終わる前に完了とみなす早すぎる完了を招く。後に控えている手順が見えていると、エージェントの注意は「終わらせること」へ向かいやすい。

悪い例:

```md
実装を十分に理解する。
```

良い例:

```md
変更する関数の呼び出し元をすべて洗い出す。
```

早すぎる完了には、次の順で対処する。

1. 完了条件を鋭くする
2. 条件をそれ以上明確にできず、実際に急ぐ様子が見られる場合に限り、手順列を分割して後の手順を見えなくする

分割で後の手順を隠せるのは、別のエージェントへの引き継ぎやサブエージェントへの委譲のように、コンテキストが実際に分かれる場合だけである。同じコンテキスト内で別の文書を呼び出しても、後の手順は見えたままになる。

### 要求水準

完了条件が、どれだけの作業を求めるかという性質である。「変更したモデルをすべて洗い出す」は、「変更の一覧を作る」より徹底した作業を求める。要求水準は、手順として書かれていない調査量を決める。

要求水準は手順だけに適用されるものではない。「すべてのルールを適用する」と書けば、参照情報だけの文書にも網羅性を求められる。

最も強い完了条件は、確認でき、かつ網羅的である。

## 分割

文書を分割すると、どちらかの負荷が増える。分割は、得られるものがそれを上回るときだけ行う。

- **手順列で分割する**: 後に控える手順が、目の前の手順を急がせている場合に分割する。逆に、手順列を統合すると、各手順から後の手順が見えるようになり、早すぎる完了を招く
- **呼び出しで分割する**: Skill に固有の判断なので、[`references/skills.md`](references/skills.md) を読む

## 中心となる語

中心となる語（leading word）は、モデルが事前学習ですでに知っている短い概念で、エージェントが文書を実行するときの考えの軸になる。「トレーサーバレット」「霧の中（fog of war）」などがこれにあたる。同じ語を文ではなく語として繰り返し使うと、文書全体からその語の定義が形作られ、少ないトークンで一連の行動を固定できる。

独自の語を作ってもよいが、明確に定義する必要がある。作った語はモデルの既存の知識を引き出せないため、定義にトークンを払うことになる。まず既存の語を探す。

中心となる語は、2つの場面で働く。

- **本文**: 語が現れるたびに、エージェントは同じ行動を取る。参照情報の中では、探すべき対象に注意を向けさせる
- **参照**: プロンプト、文書、コードで同じ語を使っていると、エージェントはその語から参照先へたどり着きやすくなる

3箇所で同じ3つの形容を並べている、1つの考えを示すために参照が1文を費やしている、といった箇所は、1語にまとめられる可能性がある。

- 「高速で、決定的で、オーバーヘッドが小さい」→ tight（tight なループ）
- 「信頼できるループ」→ red（ループがバグで red になるかどうか、という2値で観測できる状態にする）

トークンが減り、エージェントが考えるときの手がかりも鋭くなる。どの文書にも、中心となる語に置き換えられる言い換えがあると考えて探す。

## 望む行動を書く

禁止で行動を制御すると、禁止した行動がコンテキストに入り、かえってその行動が起こりやすくなる。否定は弱い修飾にすぎず、強く想起された概念に負けるため、禁止が半ば指示として読まれる。

禁止の代わりに、望む行動を直接書く。

悪い例:

```md
不要なコメントを書かない。
```

良い例:

```md
コメントはコードから分からない理由を説明するときに書く。
```

禁止が必要なのは、望む行動として言い換えられない、厳格な制約の場合だけである。その場合も、望む行動を併記して、注意がすべきことに向くようにする。

## 整理と削減

### 情報の正本

ひとつの意味は、ひとつの正本に置く。そうすれば、行動を変えるときの編集は1箇所で済む。同じ意味を複数箇所に書くと、保守とトークンのコストがかかり、その意味が本来より目立って階層を乱す。

環境も正本である。`package.json` のスクリプト、設定ファイル、ディレクトリ構成、`--help` の出力などを文書に書き写すと、その文書は陳腐化しうるキャッシュになる。キャッシュが割に合うのは、調べるコストが高い場合だけである。文書には、調べても分からない情報を書く。

- 暗黙の規約
- 判断の理由
- 設定からは分からない落とし穴

### 関連性

各行が、今も文書の目的に関係しているかを確認する。最初から作業に関係しない説明や、参照の先へ移すべき分岐は、関連性がない。記述している行動や環境が変われば、行は古くなる。

整理しないと、追記は安全で削除は危険に感じられるため、古い記述が堆積する。堆積した文書では、有効な記述を探すために層を掘り進めることになる。編集を追記だけで終えず、削除、置換、統合、分離を検討する。

### 行動を変えない指示

モデルが通常行うことを繰り返す指示は、負荷を払うだけで何も伝えない。1文ずつ、その文を消したときにエージェントの行動が変わるかを確認する。

判断の基準はモデルの通常動作であり、読み手の人間ではない。意見が分かれたら、議論ではなく文書を実際に動かして確かめる。行動を変えない文は、語を削って短くするのではなく、文ごと削除する。

中心となる語も同じ基準で確認する。「丁寧に」のように、通常動作を超えられない弱い語は行動を変えない。手法を変えるのではなく、より強い語に置き換える。

### 確認項目

編集やレビューでは、各記述を次の観点で確認する。

- 今も必要か
- 他の場所と重複していないか
- 環境から容易に調べられないか
- モデルの通常動作と同じ指示になっていないか
- 一部の分岐だけで必要な情報を、参照の先へ移せないか
- 言い換えの繰り返しを、中心となる語にまとめられないか

重複、堆積、行動を変えない指示が見つからなくなり、実際に動かして期待どおりに動けば完了とする。
