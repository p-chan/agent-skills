# 指示ファイルを書くとき

文書が `AGENTS.md` や `CLAUDE.md` などの指示ファイルのときに、[`SKILL.md`](../SKILL.md) の原則に加えて判断することをまとめる。

指示ファイルは、セッションの開始時に自動で読み込まれる。どんな作業でも読み込まれるので、コンテキストの負荷がいちばん大きい置き場である。10回に1回しか使わない情報でも、残りの9回分の負荷がかかる。長くなるほど指示が守られにくくなり、大事なルールが埋もれる。短くて正確な指示ファイルのほうが、曖昧なルールを並べた長い指示ファイルよりも役に立つ。

指示ファイルは強制力のある設定ではなく、エージェントが従おうとする文脈にすぎない。例外なく守らせたいことは、hook、lint、CI などで機械的に強制する。

## 書くこと

指示ファイルには、そのファイルが効く範囲のほとんどの作業で必要になり、エージェントが推測できないことを書く。

| 書く                                        | 書かない                                                     |
| ------------------------------------------- | ------------------------------------------------------------ |
| 推測できないビルド、テスト、lint のコマンド | コードを読めば分かること                                     |
| ツールの標準と違う決まり                    | 言語の標準的な書き方など、エージェントがすでに知っていること |
| ブランチ名、コミット、PR の慣習             | 詳しい API ドキュメント（参照先だけを書く）                  |
| プロジェクト固有の設計判断とその理由        | 頻繁に変わる情報                                             |
| 開発環境の癖（必要な環境変数など）          | 長い説明やチュートリアル                                     |
| 何度も起きる落とし穴                        | ファイルごとの説明                                           |
| 何をもって完了とするかと、その確かめ方      | 「きれいなコードを書く」のような当たり前の指示               |

ディレクトリ構成やアーキテクチャの概要のうち、コードを見れば分かることは書かない。主要なディレクトリの役割や、エージェントがファイルを読みすぎるときにどこから読むべきかなど、コードからは分からないことだけを書く。

## どこに書くか

情報は、それが効く範囲に合わせて置き場を選ぶ。

| 効く範囲                                 | 置き場                                                                    |
| ---------------------------------------- | ------------------------------------------------------------------------- |
| リポジトリのほとんどの作業               | ルートの指示ファイル                                                      |
| 特定のディレクトリやファイル             | そのディレクトリの指示ファイル、パスで対象を絞ったルール                  |
| 特定の作業、何段階もある作業             | Skill                                                                     |
| 詳しい設計や仕様                         | `docs/` などの文書                                                        |
| 例外なく守らせたいルール                 | hook、lint、型チェック、CI                                                |
| 自分だけの好み（口調、説明の詳しさなど） | ユーザー単位の指示ファイル（`~/.codex/AGENTS.md`、`~/.claude/CLAUDE.md`） |

プロジェクト固有だからといって、ルートの指示ファイルに書いてよいことにはならない。リポジトリの指示ファイルには、チームとコードベースのルールを書く。

ファイルを分けても、起動時に読み込まれるなら負荷は減らない。たとえば Claude Code の `@path` によるインポートは、整理には役立つが、起動時にすべて読み込まれる。負荷を減らしたいなら、パスで対象を絞ったルール、Skill、条件つきの参照を使う。

## 詳しい情報の参照

指示ファイルには、詳しい情報そのものではなく、それをいつ読むかと参照先を書く。

悪い例:

```md
作業前に `docs/` 以下をすべて読む。
```

良い例:

```md
DB スキーマを変更するときは `docs/database.md` を参照する。
```

## 読み込まれ方

どの指示ファイルをどの順番で読み込むかは、エージェントによって違う。2026-09-27 時点の公式ドキュメントによると、次のとおりである。

| 項目         | Codex                                                        | Claude Code                                                                                                              |
| ------------ | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| 読み込む範囲 | プロジェクトのルートから作業ディレクトリまでの各ディレクトリ | 作業ディレクトリとその上の各ディレクトリ。下のディレクトリのファイルは、そのディレクトリのファイルを読んだときに読み込む |
| 優先順位     | 作業ディレクトリに近いファイルほど後ろにつながり、優先される | 作業ディレクトリに近いファイルほど後ろにつながる                                                                         |
| 大きさの目安 | 合計が 32 KiB（既定値）を超えると、それ以降は読み込まない    | 1ファイル200行以内を推奨                                                                                                 |

Claude Code は、既定では `CLAUDE.md` がないときにだけ `AGENTS.md` を読む。両方のエージェントで同じ指示を使うなら、`AGENTS.md` を正本にして、`CLAUDE.md` に `@AGENTS.md` と書いて読み込ませる。Claude Code だけに向けた指示は、その下に書く。

## 確認項目

指示ファイルの編集やレビューでは、[`SKILL.md`](../SKILL.md) の確認項目に加えて、次を確かめる。

- その指示ファイルが効く範囲の、ほとんどの作業で必要か
- もっと範囲の狭い指示ファイル、Skill、文書に移せないか
- 機械的な強制に置き換えられないか
